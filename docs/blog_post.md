# 학폭 나침반 — RAG 로 학폭위 절차 안내 앱을 만들었지만, 변호사법 때문에 출시를 고민 중이다

![학폭 나침반 앱 아이콘](../assets/branding/icon-rounded.png)

> **한 줄 소개**
> 학교폭력대책심의위원회(이하 학폭위) 관련 **법령·절차·조치사항을 출처 인용과 함께 자연어로 답해주는** RAG 기반 안드로이드 앱.
> Flutter 클라이언트 + FastAPI 백엔드 + AWS Bedrock(Claude) 조합으로 만들고, AWS 서울 리전에 직접 배포한 뒤 Google Play 내부테스트까지 올렸다.

---

## 1. 왜 만들었나

학교폭력 사안이 발생하면 학부모/교사는 **"내가 지금 어느 단계에 있고, 며칠 안에 뭘 해야 하는지"** 가 가장 막막하다. 법령은 공개돼 있지만 한 번 읽고 정리하기에는 너무 흩어져 있고, 단순 검색 챗봇은 "출처 없는 단정"이 위험한 도메인이다.

그래서 만들고 싶었던 건 두 가지였다.

1. **출처가 박힌 답변** — 법령 조문 ID·항·호까지 인용 칩으로 노출.
2. **개인 사안 노트 톤** — "당신의 사례에 대한 법률 자문"이 아니라, **"공개 법령을 정리한 절차 안내"** 임을 시각·문구·면책 배너로 분명히.

## 2. 구조 한눈에

```
┌───────────────────────────┐        SSE          ┌──────────────────────────────┐
│  Flutter (Android)        │  ───────────────▶   │  FastAPI                     │
│  Riverpod · go_router     │                     │  Hybrid Search (pgvector)    │
│  flutter_markdown_plus    │  ◀───────────────   │  Claude (AWS Bedrock) Stream │
│  flutter_secure_storage   │                     │  Guardrails · 모델 라우팅      │
└───────────────────────────┘                     └──────────────────────────────┘
                                                              │
                                                              ▼
                                                  ┌──────────────────────────────┐
                                                  │  PostgreSQL 16 + pgvector    │
                                                  │  학폭예방법 + 행정규칙 304청크 │
                                                  └──────────────────────────────┘
```

- **인프라**: AWS Elastic Beanstalk Single Instance (`t4g.nano`, AL2023) · CloudFront + ACM 으로 `school-advisor.sedoli.co.kr` HTTPS.
- **LLM**: 초기엔 Anthropic 직호출 → 운영 단계에서 **AWS Bedrock Claude** 로 전환(서울 리전 레이턴시 + 비용 + 결제 일원화).
- **검색**: 학폭예방법 본법·시행령·관련 행정규칙을 청크 단위(총 304개)로 임베딩 + BM25 하이브리드.

## 4. 신경 쓴 UX 디테일

### (1) 인용 칩 — 답변 본문에 출처를 박는다
답변 스트리밍이 끝나면 SSE 의 `event: citation` 으로 받은 조문 ID 리스트를 **칩으로 변환**, 탭하면 `/api/v1/laws` 호출 → 바텀시트로 조문 원문을 보여준다.

> *(여기에 채팅 화면 스크린샷 — 인용 칩이 보이는 답변 메시지)*

### (2) 개인정보 입력 차단 — 이중 방어
입력창 `onChanged` 에서 정규식으로 **주민번호 / 휴대폰 / 실명 학교명** 을 감지해 전송 전 다이얼로그 + 자동 마스킹. 백엔드도 동일한 sanitize 를 한 번 더 돌린다.

```dart
final _ssnRegex = RegExp(r'\d{6}[-\s]?[1-4]\d{6}');
final _phoneRegex = RegExp(r'01[016-9][-\s]?\d{3,4}[-\s]?\d{4}');
final _schoolRegex = RegExp(r'\S{1,8}(초등학교|중학교|고등학교)');
```

### (3) "개인 사안 노트" 톤 재정렬 (모델 D)
초기엔 "AI 가 자문해 드립니다" 톤이었지만, 법률 자문으로 오해받지 않도록 **"공개 법령을 당신의 상황 메모 옆에 정리해 둔다"** 컨셉으로 카피·단계 라벨을 전부 갈았다. (`feat(copy): 모델 D — "개인 사안 노트" 카피 재정렬`)

### (4) 면책 배너 자동 부착
백엔드 답변 끝에 면책 문구가 이미 포함돼 있어도, **클라이언트가 시각적으로 한 번 더 강조**해서 답변 버블 하단에 띄운다. 톤이 약해지는 걸 백엔드 한 곳에 맡기지 않는다.

---

## 5. SSE 스트리밍 — 가장 공들인 부분

백엔드는 `text / citation / done / error` 4개 이벤트를 표준 SSE 프레임으로 보낸다. 클라이언트는 이걸 **순수 Dart 로 디코딩** 했다(패키지 의존성 줄이고 테스트 가능하게).

```
event: text
data: {"delta":"학교폭력예방법 제17조에 따르면..."}

event: citation
data: {"law_id":"학폭예방법-17","title":"피해학생 보호조치"}

event: done
data: {}
```

`event: error / code: quota_exceeded` 는 HTTP 200 을 유지하면서 스트림 안에서만 도달하므로, **사용량 초과 UX 를 끊김 없이** 노출할 수 있다.

## 6. 운영하면서 배운 것

- **벡터 DB 를 따로 띄우지 않아도 된다.** 1만 청크 미만이면 pgvector 하나로 충분하고, RDS 백업/스냅샷에 같이 묶이는 게 운영 이점이 더 크다.
- **LLM 공급자는 결제 단위로 묶어라.** Anthropic 직호출 → Bedrock 전환은 *성능 차이* 보다 **AWS 청구서 한 장으로 통합** + 서울 리전 레이턴시가 결정타였다.
- **면책·출처 인용은 백엔드 책임으로 못 박는다.** 클라이언트에서 후처리하기 시작하면 톤이 분기된다. 백엔드를 단일 진실 원천으로.
- **Riverpod 코드 생성은 우리 규모엔 과했다.** raw provider 만으로 충분히 깔끔하고, 빌드러너 사이클이 빠지니까 반복 작업이 가벼워졌다.

## 8. 왜 출시를 멈췄나 — 변호사법

기술은 다 만들어졌고 Play 내부테스트까지 돌렸지만, **정식 출시는 보류** 중이다. 이유는 한 줄로 **변호사법 제109조**.

> **변호사법 제109조(벌칙)**
> 변호사가 아니면서 금품·향응 또는 그 밖의 이익을 받거나 받을 것을 약속하고
> 법률사건이나 법률사무에 관하여 감정·대리·중재·화해·청탁·법률상담 또는
> 법률 관계 문서 작성, 그 밖의 법률사무를 취급한 자는 처벌한다.

핵심 쟁점은 두 가지다.

**(1) "유료 + 법령에 대한 응답" = 법률사무 취급으로 볼 여지가 있다.**
이 앱은 학폭예방법 본법·시행령·관련 행정규칙을 RAG 로 검색해 자연어로 응답한다. 아무리 "공개 법령을 정리해 드립니다" 라고 포지셔닝해도, **사용자의 구체적 사안에 대해** 절차/조치를 안내하는 순간 — 그리고 그 대가로 **이용권을 받는** 순간 — 109조의 "법률상담 또는 법률사무 취급" 으로 해석될 위험이 남는다. 무료 정보 제공이면 결이 다르지만, BM 을 인앱결제로 잡은 시점에서 회색지대 한복판에 들어간다.

**(2) "정보 제공" 과 "자문" 의 경계는 UX 가 결정한다.**
"제17조에 따르면 피해학생 보호조치는 ~~~ 입니다" 는 정보 제공에 가깝다.
"당신의 경우 학교장 자체해결 요건을 충족하므로 ~~~ 하시면 됩니다" 는 자문에 가깝다.
RAG + LLM 은 사용자 질문이 구체적일수록 후자 쪽 답변을 자연스럽게 생성한다. 시스템 프롬프트로 톤을 누르고, 모든 답변 끝에 면책 배너를 붙이고, "개인 사안 노트" 라는 컨셉으로 카피를 모두 갈아엎은 것도 (커밋 `feat(copy): 모델 D — "개인 사안 노트" 카피 재정렬`) **109조 해석의 무게중심을 정보 제공 쪽으로 끌어내려는 시도**였다.

그럼에도 "출시해도 되는가" 에 대해 **스스로 확신할 수 없다**. 법률 리스크는 기술로 0 으로 만들 수 없는 종류의 리스크다.

### 떠올려본 대안들

- **유료 모델 자체를 빼고 무료/광고형으로 전환** — 109조의 "금품·이익" 요건을 떼어내는 방향. 다만 BM 이 사라지면 운영비(Bedrock + EB + 도메인)를 감당할 동기가 약해진다.
- **응답을 "조문 인용 + 정의" 로만 제한** — 절차/판단 안내를 코드 단에서 자르고, 사용자가 질문해도 "관련 조문은 X 입니다" 만 답하도록 강제. 사실상 법령 검색기로 다운그레이드.
- **변호사 또는 법무법인과 공식 협업** — 사명을 변호사가 운영하는 서비스로 두고 기술만 제공. 가장 안전하지만 1인 개발 범위를 넘는다.
- **법무 자문을 받아 면책 구조를 문서화** — 약관·UX·BM 을 한 묶음으로 외부 의견서 받고 그 결과에 맞춰 결정.

**현재 상태는 단순하다 — 앱은 다 만들었고, 그 다음 한 발을 아직 못 떼고 있다.** 정식 출시도, 법무 자문도, 위 대안 중 어느 쪽으로 방향을 잡지도 못한 채로 멈춰 있다.
